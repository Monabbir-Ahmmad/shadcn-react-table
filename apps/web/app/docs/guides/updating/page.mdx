# Updating your copy

`shadcn add` copies this block's source into your project — after that,
the code is yours, and upstream releases don't reach it automatically.
This page is the manual update path.

## Know what you have

Every release stamps its version into the registry item. When you
install, note the `meta.version` of
[`/r/data-table.json`](/r/data-table.json) somewhere in your project
(a comment, your PR description). The
[changelog](https://github.com/Monabbir-Ahmmad/shadcn-react-table/blob/main/packages/shadcn-react-table/CHANGELOG.md)
lists what changed in each version.

## Update recipe

1. Start from a clean branch.
2. Re-run the install command with `--overwrite`:

   ```bash
   npx shadcn@latest add --overwrite <registry-url>/r/data-table.json
   ```

3. Review the diff. Everything under `components/ui/data-table/` is
   replaced with the new upstream source — `git diff` shows upstream
   changes mixed with the loss of any local edits you made.
4. Re-apply your local edits on top, or cherry-pick hunks with
   `git checkout -p` against the pre-update commit.
5. Check the changelog for entries marked as breaking and adjust your
   usage.

<Callout variant="tip" title="Keep local edits separate">
  The less you edit the copied files directly — prefer wrapping the
  table or using the many `render*` slots — the closer step 3's diff is
  to a pure upstream update.
</Callout>

## Upgrading to 0.5.0 (TanStack Table v9)

0.5.0 moves the engine to TanStack Table v9. Re-add the block, then:

1. **Type columns with `DataTableColumnDef`.** TanStack v9's `ColumnDef` needs a
   feature-set type parameter; ours supplies it.

   ```ts
   import type { DataTableColumnDef } from "@/components/ui/data-table"
   const columns: DataTableColumnDef<Person>[] = [...]
   ```

   `DataTableRow`, `DataTableColumn`, `DataTableCell`, and `DataTableHeader` are
   the matching instance types. Install `@tanstack/react-table@^9` and
   `@tanstack/match-sorter-utils@^9` (the registry item pins both).

2. **Drop row-model options.** `getCoreRowModel`, `getSortedRowModel`, … are no
   longer accepted; the table wires every row model itself.
3. **Custom aggregation functions** use TanStack v9's
   `constructAggregationFn({ aggregate })` shape. Built-in names (`"sum"`,
   `"mean"`, …) are unchanged.
4. **Instance APIs follow TanStack v9:** `column.pin("start" | "end")`,
   `column.getIsPinned()` returns `"start" | "end"`, `getPrePaginatedRowModel()`.
   Table options and `table.getState()` keep the `left`/`right` pinning shape and
   the `columnSizingInfo` name.
5. **Don't destructure row/column/cell methods** (`const { getValue } = row`); call
   them on the object. Cell-renderer `({ getValue })` still works.
6. **Row data must satisfy TanStack's `RowData`** (`Record<string, any> | Array<any>`).
   `unknown` is no longer accepted, so use a concrete row type for
   `useDataTable<TData>` and `DataTableInstance<TData>`. `DataTableInstance`
   with no type argument now defaults to `RowData`.
7. **Render contexts are unchanged.** Column renderers (`cell`, `header`,
   `footer`, `aggregatedCell`) still receive the enriched instance, so
   `({ table }) => table.getState()` and `table.tableInstance` type-check and
   work as before. TanStack v9's own contexts don't include `getState`.
8. **`table.options` is the options object you passed in** on the latest render
   (TanStack v9's React adapter behavior), not TanStack's internally merged
   options with feature defaults.
9. **A small TanStack feature is registered by the block.** Its types add
   `dataTableInstanceFeature` through TanStack's `Plugins` / `Table_FeatureMap`
   interfaces, scoped to tables built with the block's feature set. Other
   TanStack tables in your app are unaffected, except ones typed
   `Table<any, …>`.
